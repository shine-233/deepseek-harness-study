## 先分清 5 分钟和 15 分钟

前 5 分钟只做两件事：读[从零开始读 DSH](./00-开始这里.md)的六个词，并打开[仓库地图](./01-仓库地图.md)看目录分工。做到这里，你已经知道 DSH 在解决什么问题，可以先停下来。

完整的 15 分钟产出再多做三件事：选择一条路线、打开一个固定版本源文件、写下用途、设计原因、源码证据和未验证范围。这样“认识 DSH”和“完成一次源码阅读记录”不会被混成一个模糊的时间承诺。

## 做完以后你会得到什么

你会完成一份最小学习记录：知道 DSH 的一个概念、找到一个固定版本源文件、说清它解决什么问题，并写下当前还没有被运行验证的地方。

这份记录比“我看过很多页面”更有用，因为它留下了一个可以继续追踪的源码入口。

## 第一步：只打开学习首页

打开 [DSH 源码学习首页](https://shine-233.github.io/deepseek-harness-study/)，点击“第一次来，按这里走”，再打开[从这里开始](../START-HERE.md)。第一次不要点 `Code`，不要创建 Codespace，也不要从逐文件索引第一页开始顺序阅读。

如果你已经在 GitHub 仓库页面，点击 README 最上方的[开始学习入口](../START-HERE.md)也可以；它和 Pages 的学习入口指向同一条路线。

## 第二步：只读两篇基础课

先读[从零开始读 DSH](./00-开始这里.md)，只记住“插件、服务、事件、Profile、Bundle、Turn”六个词；再读[仓库地图](./01-仓库地图.md)，只回答“功能包放在哪里、启动从哪里开始、测试线索在哪里”三个问题。

读不懂时不要跳到索引。回到这两篇文章，把问题改写成“它接收什么、产出什么、由谁使用”，再继续往下读。

## 第四步：找到一个固定版本文件

在[逐文件索引导航](./文件索引/README.md)中选一个功能组，例如 `packages/core`；打开其中一张文件卡片，再点击卡片里的固定源码链接。

文件卡片是定位工具，不是逐行人工翻译，也不是运行时证明。你要把卡片的解释和固定提交源码对照一次，看看“用途”和“直接协作者”是否符合源码事实。

## 第五步：复制这张学习记录

把下面的模板复制到自己的 GitHub gist、个人笔记或仓库分支中，填完它就是你的第一次学习产出。

```text
我今天研究的问题：

我选择的源文件：

这个文件解决什么问题：

为什么它独立放在这里：

它的直接协作者或下一跳：

我在固定提交源码中看到的证据：

我现在已经证明了什么：

我还没有证明什么：

下一步要读的源码或测试：
```

“我还没有证明什么”必须填写。比如，看到 system prompt 里组装了工具 schema，可以支持“工具定义会进入组装路径”的静态结论；不能只凭这个结论写成“某个 provider 的 token、缓存命中率或模型质量已经实测”。

## 先看一份填好的答案

下面不是唯一正确答案，只是让第一次做任务的人知道“写到什么程度就可以停”。它选择了学习示例里的公开观察事件，没有把静态测试包装成真实 DSH 运行：

```text
我今天研究的问题：一个插件能不能只观察工具结果，而不改写工具行为？

我选择的源文件：study-examples/minimal-observer-plugin/src/index.js

这个文件解决什么问题：订阅 tools/result，校验配置，并把文本结果压缩成限长预览。

为什么它独立放在这里：观察逻辑、配置校验和示例测试可以先在不启动 DSH 的情况下单独理解；以后换成真实 Loader 时，失败范围更容易定位。

它的直接协作者或下一跳：tests/plugin.test.js、cordis.patch.yml，以及真实安装时的 Profile/Loader。

我在固定提交源码中看到的证据：入口调用公开的 ctx.on('tools/result', ...)，测试断言预览限长且传入结果没有被修改。

我现在已经证明了什么：示例自己的事件登记、配置校验和预览行为通过 Node 单元测试；JavaScript 通过示例 lint。

我还没有证明什么：真实 DSH Profile/Loader 已加载它、Fiber 卸载无残留、模型 token 变少、跨版本兼容或安全性。

下一步要读的源码或测试：study/19-插件测试卸载与版本证据.md，再决定是否补 Loader 组合测试。
```

如果你还不知道一个文件的“为什么”，先写“我从源码看到的边界”，不要凭感觉补一句漂亮的设计理由。学习记录的价值在于能让下一个人回到同一个固定文件继续核对。

## 如果你研究“万物皆插件”，照这个顺序问

先读[工具预算与插件责任决策卡](./27-工具预算与插件责任决策卡.md)，再问“插件化解决了什么”：它让能力可以装配、替换、提供和卸载；它不要求每个 agent 每轮把全部工具都交给模型。

再问“工具现在在哪一层”：分别记录已注册集合、当前 agent 可解析集合、`presentAs()` 与最终组装出的模型呈现，以及这次执行是否被允许。在 DSH 的同一 agent 作用域中，`restrict()` 会同时影响工具查找和 native schema 组装；被筛掉的工具会像未知工具一样不能由该 agent 分发。不要把“界面没显示”当成“模型没收到”，也不要把“模型看不见”当成“操作系统权限已经收紧”。

最后问“谁应该改什么”：普通插件优先使用公开服务、事件、工具注册和 Bundle；缺少公开扩展点时由宿主维护者提出接口或维护 patched fork；读取私有 registry、模块缓存、进程或注册表的方案必须单独标成运行时补丁或注入器。

## 什么时候才需要打开 Codespaces

只读文章、固定源码链接和索引：留在 GitHub 网页或 Pages。

想搜索文件、写少量 Markdown 笔记：可以打开 [`github.dev`](https://github.dev/shine-233/deepseek-harness-study)，但它没有终端，不能证明 DSH 或插件已经运行。

想执行离线索引检查器、构建文档或做隔离实验：先读[GitHub 网页、github.dev 与 Codespaces 学习路线](./21-GitHub网页与Codespaces学习路线.md)，再考虑 Codespaces 的额度、费用和清理。

想跑真实模型 A/B 实验：还需要固定模型、provider、工具集合、上下文、平台和时间，并保存脱敏快照；不能用一次网页阅读替代实验。
