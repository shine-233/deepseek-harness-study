# 怎样使用逐文件索引

`study/文件索引/` 不是把 2,756 个文件复制一遍，而是给每个真实源文件放一张小卡片。卡片上的路径链接固定到官方提交，便于从中文解释回到原始代码。

## 每条记录的字段

- **所属层**：它属于 `packages`、`apps`、`vendor` 或其他哪一层。
- **文件角色**：入口、类型契约、适配器、运行时、工具、测试等。角色根据路径和文件名生成，用来帮助第一次定位。
- **这个文件有什么用**：用不依赖具体代码细节的语言回答“它解决哪个问题”。
- **为什么这样设计**：解释拆成单独文件的常见工程原因，例如替换、测试、生命周期和边界。
- **直接协作者**：优先列同包 README、同目录文件和同包测试，帮助你沿依赖方向继续读。
- **对应测试**：按同目录或同包、同名线索寻找测试。没有找到不代表没有测试，只代表路径不能安全地自动判断。
- **阅读顺序**：给出从 README 到入口、实现和测试的最短路线。
- **固定版本与证据**：记录归档扫描到的行数和声明；关键文件会链接到人工精读。

## 自动索引和人工精读的区别

自动索引保证“每个源文件都有一条对应记录”，并且由 [生成器](../study-tools/generate-source-index.mjs) 根据 Git tree 重新生成。它不声称已经理解每个函数的全部语义，尤其不会替代异常路径、并发和权限审查。

人工精读集中在官方主链路：Cordis、Profile、Bundle、Session、Agent、Agent Loop、工具、LLM 和 CLI。它们在[核心文件精读](03-核心文件精读.md)中逐文件说明用途、设计原因、协作者和测试；其他条目先作为可追踪入口，再按需要深入。

## 覆盖怎样验证

在仓库根目录执行：

```powershell
$manifest = Get-Content -Raw study/source-index-manifest.json | ConvertFrom-Json
$headings = (Get-ChildItem study/文件索引 -File | Select-String '^### ').Count
"清单文件数: $($manifest.files.Count)"
"索引标题数: $headings"
```

当前两个数字都应为 `2756`。还可以重新运行生成器，检查它打印的提交和数量是否与 `UPSTREAM.md` 一致。这个检查证明的是路径覆盖，不证明 DSH 能构建、能连接真实模型或所有测试都通过。

## 怎样从一条记录继续追代码

先打开它所在包的 README，确认包公开的服务和限制；再看入口文件的导出，接着沿直接协作者读类型、事件和实现；最后读测试，观察作者如何验证成功、失败、取消和边界情况。若条目位于 `vendor/`，先看第三方许可证和上游说明。

## 为什么选择分片索引

一个 Markdown 文件放 2,756 条记录会很难搜索、加载和审阅。现在按顶层目录和 `packages` 功能组拆成 66 页，既保留“一文件一条”的精确对应，也让读者可以先选择自己关心的层。生成器负责清单，人工文档负责解释，两者的职责不会互相覆盖。
