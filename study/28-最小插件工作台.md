# 最小插件工作台：构建 → 注册 → 卸载

这是一项可以在本地真正跑起来的离线实验：用仓库自己的 TypeScript 编译器构建一个插件，用真实 Cordis `Context` 和 Loader 加载构建产物，再移除 Loader entry，检查插件提供的服务已经消失、计时器已经清理。它只证明最小插件生命周期，不证明完整 DSH Host、Web、CLI、模型请求或跨平台发布兼容性。

## 你要得到什么

完成后，你应能解释三件事：`tsc` 怎样把 `src/minimal-plugin.ts` 变成 `dist/minimal-plugin.js`；Loader 怎样从构建后的模块创建一个 entry 并激活插件 Fiber；`ctx.loader.remove()` 怎样触发 Fiber 的 effect 清理、取消心跳计时器并注销服务。

工作台位于 [`study-tools/minimal-plugin-workbench`](../study-tools/minimal-plugin-workbench/README.md)。它没有真实模型、API key、HTTP 服务或网络依赖，适合在 Codespaces 或本机先完成第一条运行证据。

## 先安装和构建

在仓库根目录执行：

```sh
pnpm install
pnpm --dir study-tools/minimal-plugin-workbench run build
```

构建命令只编译 `src/minimal-plugin.ts`，并在被忽略的 `dist/build-manifest.json` 中记录构建入口和 SHA-256。构建失败时不要手动创建 `dist/minimal-plugin.js`；运行器会拒绝缺少构建产物的状态。

## 运行真实 Loader 闭环

```sh
pnpm --dir study-tools/minimal-plugin-workbench run verify
```

运行器实际执行下面的动作：

1. 创建新的 Cordis `Context`，安装真实 `@deepseek-ai/cordis-plugin-loader`。
2. 让 Loader 从 `dist/minimal-plugin.js` 创建一个 entry；这一步是模块导入、插件注册和 Fiber 激活，不是打印一行“注册成功”。
3. 读取插件提供的 `studyMinimalPlugin` 服务，等待心跳计数增加，证明 effect 已经在运行。
4. 调用 `ctx.loader.remove(entryId)`，等待 Loader 完成卸载。
5. 断言服务不再能从 Context 读取、entry 数量为零、服务快照进入 `disposed`，并确认心跳清理函数已经写入清理时间。

成功输出类似下面的结构；`entryId` 每次可能不同，因为 Loader 为未指定 id 的临时 entry 生成唯一 id：

```json
{
  "result": "PASS",
  "registration": {
    "service": "studyMinimalPlugin",
    "phase": "active",
    "tickCount": 6
  },
  "unload": {
    "phase": "disposed",
    "serviceAbsent": true,
    "entriesRemaining": 0,
    "heartbeatStable": true
  },
  "externalServices": {
    "modelRequests": 0,
    "networkRequests": 0
  }
}
```

这里的 `tickCount` 是插件自己的定时器对实际生命周期的可观察信号；它不是模型调用，也不是用固定文本伪造的结果。`serviceAbsent: true` 和 `entriesRemaining: 0` 才是卸载断言的重点。

## 证据边界

该实验是固定源码仓库中的最小 Context/Loader 运行证据。它没有覆盖 DSH profile/bundle 组合、真实 Host/Web 端口、浏览器交互、第三方 npm 安装、真实模型、凭据、子进程、跨平台行为或生产发布门禁。若要把插件提升为可分发扩展，仍需按 [插件测试、卸载与版本证据](19-插件测试卸载与版本证据.md) 增加 Loader 组合、构建后消费者、失败、取消、真实宿主和平台矩阵证据。
