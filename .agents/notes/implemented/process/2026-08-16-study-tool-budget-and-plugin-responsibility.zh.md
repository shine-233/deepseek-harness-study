# Agent Note: 增加工具预算与插件责任决策卡

Status: implemented

[English](2026-08-16-study-tool-budget-and-plugin-responsibility.md) | 中文

## Problem

现有学习路线已经分别解释工具可见性、公开扩展点、Hook bridge、patched fork 和运行时注入器，但第一次来的读者仍要自己综合多篇文章，才能判断眼前的项目属于哪一类。仓库 README 和 Pages 入口需要一个短而直接的决策面。

## Decision

新增 `study/27-工具预算与插件责任决策卡.md` 作为面向初学者的中文汇总。它定义已注册、模型可见和执行允许三层工具状态；给出六层社区生态地图；区分普通插件作者与宿主／发行版维护者；提供五问分类卡和十分钟社区审计卡；并按只需网页、需要学习仓库、需要宿主维护者、需要 provider 或需要仓库管理权限来排列未来工作。仓库 README、Pages 首页、`START-HERE.md`、15 分钟任务单、使用手册和相关工具／插件课程都链接到这张卡。

本篇采用直接定义，不使用比喻。它继续保留证据边界：离线快照不是 provider token 数，静态源码不是运行证明，有 Bundle 外壳的项目仍可能包含单独的注入层。

## Alternatives considered

**继续让现有文章彼此分开。** 每篇文章本身是准确的，但读者必须自己拼出分类和责任边界；保留详细课程的同时增加一张决策卡，可以减少这一步综合成本。

**把所有导出 `apply(ctx)` 的项目都叫插件。** 这会抹掉公开 Cordis 集成、Bundle 组合、patched fork 以及进程／操作系统级注入之间的差异，因此决策卡分别判断实现层和责任归属。

**用比喻让主题更简单。** 仓库写作规范要求使用直接技术术语、不使用比喻。因此决策卡使用三层直译和具体证据字段，不使用可能被误解成实现事实的类比。

## Consequences

GitHub 仓库和 Pages 首页现在为关心工具列表过长或插件身份的读者提供一条统一路线。工具、插件、Hook 和社区审计路线都会先经过同一个分类节点，再进入详细材料。新卡改善了导航和学习清晰度；它没有创建运行时可见性 API，没有运行真实模型 A/B，也没有为任何第三方项目做安全认证。
